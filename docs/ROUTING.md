# 路由：谁会接到这件事

静静把一句话交给哪个 Worker，按固定顺序判断。原则是 **Agent 提名、代码裁决**：模型可以理解模糊说法并提出建议，但最终选择要经过代码校验，并且能解释。

## 决策顺序

只看主人自己的消息（Web / 配对的 Telegram / 拍板里的自定义决定）。外部来源（邮件、企微、Webhook）只走「工作流程 / 分配规则」，见下文。

1. **明确点名**：文本命中某个 Worker 的 `aliases`（大小写、全半角、标点都不影响），或老插件的 `keywords` 正则。点名但不可用、或不具备所需硬能力时改派，并在回复里说明。
2. **工作流程指定的 Worker**：流程的 `worker` 字段优先于规则。
3. **分配规则**：命中的规则指定谁就是谁。
4. **模型选择**：Router 给的 `worker` 必须同时满足：Worker 可用、具备所需硬能力、`evidence` 原文能在用户消息里找到（防幻觉）。任一条不满足就丢弃，继续往下。
5. **具体能力**：文本点到能力（`tapd-cli`、`git`…）时，声明了该能力的 Worker 优先；没人显式声明时，具 `shell` 能力（能执行本机命令）的 Worker 作为候选。
6. **硬能力兜底**：需要 code / write-file / manage-files 时，具备该能力的 Worker 里按偏好选。
7. **兜底 Worker**：主人设置的兜底，否则最便宜的可用文本 Worker。

偏好规则：开销低优先，同开销内置优先，再按 id 排序（保证结果稳定）。质量/成本策略后续可配置。

## 每种信号谁说了算

| 信号 | 来源 | 控制方 |
|---|---|---|
| 工作流程 / 分配规则 | 用户配置 | 代码（命中即用） |
| 别名点名 | Worker manifest + 本机配置 | 代码（归一化 + 词边界） |
| 模型选择 | Router 模型 | Agent 提名，代码校验 evidence / 可用性 / 硬能力 |
| 能力 | `src/capabilities.json` + 本机勾选 | 代码收窄候选 |
| 成本/质量 | 设置 | 代码 |

## 冲突裁决

| 情况 | 结果 |
|---|---|
| 点名 A，模型/流程/规则说 B | A 赢；流程步骤、工作区保留 |
| 点名了但 A 不可用 / 不具备硬能力 | 改派并说明，不静默 |
| 模型选的 Worker 不满足文本点到的能力 | 丢弃模型选择，走能力候选 |
| 模型 evidence 在原文里找不到 | 丢弃模型选择 |
| 多个能力候选 | 模型的选择如果在候选里就用它，否则按偏好 |
| 外部来源出现点名 / 能力 / 模型信号 | 全部忽略，只认流程和规则 |

## 人话怎么变成规则

- **工作流程** `when`：默认按逗号/顿号/竖线拆成字面关键词；确实要正则时加 `whenRegex: true`；`notWhen` 排除问句/反例。
- **分配规则**：默认「关键词模式」（逗号/竖线分隔、自动转义）；老规则没有模式字段时仍按正则，兼容已存数据。
- **Worker 别名**：manifest 给默认，用户可以在「设置 → Worker → 配置」里加本机叫法。
- **能力**：内置目录在 `src/capabilities.json`；用户可以在 Worker 配置里勾选本机真能用的工具。自定义能力存在设置的 `capabilities` 里。

## 外部来源的安全边界

外部内容不能决定交给谁：邮件、群消息、Webhook 里写「用 deepseek 查」不算数，只认主人配置的工作流程和分配规则。外部消息点名 Worker 时，静静会**停下来问主人**，而不是直接改派。

## 兼容与迁移

- 老的 `keywords` 正则继续按「点名」工作；
- 老工作流程的 `when` 默认按关键词解释；如果里面用了正则语法，加一行 `whenRegex: true`；
- 老分配规则没有 `pattern_mode` 时按正则解释，新规则默认关键词；
- 没有任何别名/能力配置时，行为与之前一致。

## 已知边界（下一步）

- 多个别名同时出现、或低置信时，还没有「这次交给 A 还是 B」的确认卡片；
- 质量/成本策略还没做成按能力配置；
- 外部来源的能力识别（停下问主人时把能力也列为理由）还没接；
- 自动探测本机工具（`which tapd`）并建议勾选能力，尚未实现。
